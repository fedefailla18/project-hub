## 🔴 High Priority
- **`investracker`/`importer-porfolio` [DESIGN PROPOSED, awaiting user decision — not yet implemented]**: user surfaced a requirement that wasn't captured when PR #65 (Binance sync-job tracking) was designed: exchange-synced transactions should NOT land in the same place as the user's manually-managed portfolio data — the product intent is two comparable views (manual "Portfolio" vs API-synced "Exchanges", already reflected as separate nav sections in the FE) that the user can optionally reconcile later, not a silent merge on every sync click. Investigation found:
  - PR #65 (and every other sync path) writes into the shared `transactions` table via `TransactionService.saveIfAbsent`, scoped only by `portfolio_id` — no origin-aware separation at the table level.
  - A **portfolio-level separation mechanism already exists but is only convention, not enforced**: `Portfolio.exchangeName` + auto-created exchange portfolios (named after the exchange, e.g. "BINANCE") on saving API keys (`ExchangeConfigController`). But `POST /transaction/sync/binance(/full)?portfolio=<name>` accepts *any* portfolio name — nothing in the backend stops a sync from targeting (and silently relabeling) the user's manual portfolio; only a frontend naming heuristic in `PortfolioPage.tsx` gates which portfolios show a sync button.
  - Found a related, independent bug while investigating: `BinanceSyncService`/`MexcSyncService` (the *incremental* sync path) never set `exchangeName` on trade rows (only on deposits/withdrawals) — so incremental-synced trades are indistinguishable from manual entries at the DB level, and don't show up on the `/binance-activity`/`/mexc-activity` pages, which filter by `exchangeName`.
  - This intent was never written down anywhere in the docs (checked the just-merged consolidated `docs/*.md` — no mention of a manual-vs-exchange separation or a consolidation feature).
  - Proposed direction (not yet confirmed): harden the *existing* portfolio-level separation (backend-enforce that exchange syncs always target their dedicated auto-created portfolio, fix the incremental-sync `exchangeName` tagging gap) rather than introduce a whole new parallel transactions table — reuses the already-working `HoldingService`/P&L math (one code path, scoped by `portfolio_id`) instead of needing a second one, and "consolidate" becomes a well-scoped "merge portfolio B's transactions into portfolio A" operation on top of existing primitives.
  - Two trade-offs surfaced to the user via `AskUserQuestion` before writing any code: (1) harden portfolio-level separation (recommended) vs. a brand-new dedicated exchange-transactions table, (2) fix both incremental + full sync now vs. full sync only for now (incremental as a follow-up).
  - Also asked for: a UI quick-start guide explaining Portfolio-vs-Exchanges, and pulling latest `main` (docs consolidation, `ff9047d`) into both feature branches — done (clean merge, no conflicts) regardless of the design decision above.

  1. **Binance/MexC sync silently finds "no results" for anyone whose portfolio is mostly BTC/ETH/BNB/MX.** `BinanceSyncService`/`MexcSyncService` filtered "investment assets worth syncing trades for" through a `QUOTE_CURRENCIES` set that wrongly included BTC/ETH/BNB/MX alongside real stablecoins (USDT, DAI, etc.) — conflating "can be a quote currency for other pairs" with "not a real investment". Someone holding BTC bought against USDT gets 0 candidate trading pairs built, so `getMyTrades` is *never even called* (confirmed via `external_api_log`: zero `/myTrades` rows since 2026-08-26, only successful `/account` calls). Fixed by excluding only true stablecoins/fiat (reusing `OperationUtils.STABLE`, which the codebase already treats as canonical) — `OperationUtils.GRAND_SYMBOLS` already flags BTC/ETH as legitimate investment assets, so the old exclusion directly contradicted an existing convention in the same codebase. Also fixed `BinanceSyncServiceSpec`'s `"should not fetch any trades when all assets are quote currencies"` test, which encoded the bug as expected behavior. **Note:** the whole `BinanceSyncServiceSpec` file (all 6 pre-existing tests, now 7) fails with an unrelated NPE — confirmed via `git stash` that this predates today's fix entirely (`Mock(TransactionProcessor)` — that class doesn't exist in `src/main` anymore, only `TransactionService` does; likely fallout from the in-progress `integration/new-portfolio-syncing-app` refactor already tracked above). Did not attempt to fix that separate, bigger issue here.
  2. **IOL integration logs the user out of the entire app on any IOL-side auth hiccup.** `IolErrorDecoder` re-throws IOL's own HTTP status verbatim as a `ResponseStatusException` (e.g. 401 if IOL rejects the stored username/password during automatic token refresh in `IolTokenService`). That propagates unmodified to the HTTP response, and `importer-porfolio`'s global axios interceptor treats *any* 401 from *any* endpoint as "this app's session expired" — clearing localStorage and redirecting to `/login`. So an IOL-side credential/token problem (nothing to do with the user's own JWT) silently logs them out of the whole app ("después de invertironline la aplicación se sale"). Fixed with an `@ExceptionHandler(ResponseStatusException.class)` in `IolIntegrationController` that remaps IOL-originated 401/403 → 424 (Failed Dependency) and anything else → 502, so the FE's blanket interceptor no longer misfires; the FE's existing per-slice `catch`/`rejectWithValue` handling (already status-code-agnostic) picks it up normally.
  3. **MEXC `GET /api/v3/account` returns 400 Bad Request** (user-reported, reproducible per their pasted log). Structurally the HMAC signing code is identical to Binance's (which works) and hasn't changed since 2026-04-29; the same call succeeded on 2026-05-04 with real balance data, then started failing 2026-08-27 onward with no code changes in between — points to something external (MEXC-side key rotation/IP restriction, or an MEXC API change) rather than a code bug, but **couldn't confirm the exact reason**: the error logging only captured `e.getMessage()` ("400 Bad Request from GET ...") not the actual response body MEXC sent back. Fixed the logging gap in both `MexcApiService` and `BinanceApiService` (`WebClientResponseException.getResponseBodyAsString()` instead of `getMessage()`) so the *next* failure will show MEXC's real error code/message in `external_api_log` — needed to actually diagnose this one further. Recommend the user also check the MEXC API key's IP whitelist / validity on MEXC's own dashboard.

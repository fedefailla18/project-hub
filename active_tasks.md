## 🔴 High Priority
- **`investracker` — holdings correctness investigation (2026-10-23)**: user asked "¿calculamos holdings correctamente? ¿solo con transacciones manuales o también las de Binance?" Investigated with two parallel agents + direct code verification (not just agent reports). **Confirmed by design**: holdings have zero filter on `exchangeName`/origin — both `/portfolio/distribution` (`PortfolioDistributionFacade`) and the recompute path (`CoinInformationFacade`) read/write by `portfolio_id` alone, so a manually-entered and a Binance-synced transaction are treated identically once they're in the same portfolio's rows. Found two real, concrete correctness bugs along the way — logged as separate work items below rather than one bundle, since they have independent fixes and different urgency:
  1. **Holdings don't auto-update after an exchange sync (High — this is the one actively misleading the user right now)**. Root cause: `/portfolio/distribution` reads the persisted `Holding` table, a materialized cache of `Transaction` rows, not a live recompute — only the manual-upload path (`ProcessFileV2`) triggers the recompute (`CoinInformationService.getCoinInformationResponse`) that updates it; none of the 4 sync services do. **Design confirmed 2026-10-29** (user: must be async and resilient to failure, not synchronous — a full-sync recompute could take a while): new `HoldingRecomputeTask` entity/table, mirroring the already-proven `SyncJob`/`SyncJobChunk` + `SyncJobStartupReconciler` pattern — one row per `(portfolio, symbol)`, unique partial index on PENDING/RUNNING (upsert-as-dedupe, so rapid-fire dirty-marking from many trades on one symbol coalesces into one task). Each sync path marks `(portfolio, symbol)` dirty right after `saveIfAbsent(tx)` (cheap insert-if-absent, no ambient transaction, consistent with the existing per-row-commit philosophy). A dedicated worker processes PENDING tasks calling the same `coinInformationService.getCoinInformationResponse(...)` `ProcessFileV2` already uses — no new business logic, just reuse. **Confirmed**: near-immediate `@Async` nudge after each sync *plus* a ~20s `@Scheduled` poller as a safety net (not poller-only) — gives a near-real-time feel without depending on the nudge never being lost. **Confirmed**: backend-only for this iteration, no FE "recomputing..." indicator yet (fast-follow if ever needed). **Bonus**: this same queue cleanly resolves work item #2 below too — `consolidate()` just resets `processed=false` and marks the affected symbols dirty on both portfolios, instead of a separate inline-vs-deferred decision. Not implemented yet — this entry is the confirmed design, next step is writing the code.
  2. **`PortfolioService.consolidate()` silently undercounts the target and leaves the source stale (High)**. Root cause: `consolidate()` only moves `portfolio_id`, never resets `Transaction.processed` or touches `Holding` rows on either side — the target's next recompute silently skips already-`processed` moved transactions (filter is `!isProcessed()`), and the source keeps phantom balances. **Fix folded into item #1 above**: reset `processed=false` + mark dirty on both portfolios via the same `HoldingRecomputeTask` queue, once that exists.

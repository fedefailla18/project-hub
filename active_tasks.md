- **`investracker` — holdings correctness investigation (2026-10-23)**: user asked "¿calculamos holdings correctamente? ¿solo con transacciones manuales o también las de Binance?" Investigated with two parallel agents + direct code verification (not just agent reports). **Confirmed by design**: holdings have zero filter on `exchangeName`/origin — both `/portfolio/distribution` (`PortfolioDistributionFacade`) and the recompute path (`CoinInformationFacade`) read/write by `portfolio_id` alone, so a manually-entered and a Binance-synced transaction are treated identically once they're in the same portfolio's rows. Found two real, concrete correctness bugs along the way — logged as separate work items below rather than one bundle, since they have independent fixes and different urgency:
  1. **Holdings don't auto-update after an exchange sync (High — this is the one actively misleading the user right now)**. Root cause: `/portfolio/distribution` reads the persisted `Holding` table (`PortfolioDistributionFacade.addHoldingsToPortfolioDistribution` → `HoldingService.getByPortfolio`), which is a materialized cache of `Transaction` rows, not a live recompute. The manual-upload path (`ProcessFileV2.processFile`, `service/ProcessFileV2.java:77-80`) calls `coinInformationService.getCoinInformationResponse(symbol, ...)` for every touched symbol right after saving — that call is what actually updates `Holding`. None of `BinanceSyncService`, `BinanceFullSyncService`, `MexcSyncService`, `MexcFullSyncService` make that call anywhere (confirmed via grep — zero matches for `CoinInformation`/`HoldingService` in all four files). So after any Binance/MexC sync, the raw `transactions` table is correct immediately, but `/portfolio` keeps showing pre-sync numbers until someone separately hits `/transaction/information/all/{portfolio}`. Not a caching bug (no cache sits in front of `Holding`) — it's a missing call. **Proposed fix**: have each sync path call the same per-symbol recompute `ProcessFileV2` already does, for every distinct symbol touched during that sync run. **Open question before implementing**: incremental sync (small deltas) can probably recompute immediately and synchronously; full-sync (years of history, many symbols, already job/chunk-tracked and async) needs a decision on *when* — per completed chunk (noisy), per completed job/entity-type, or only once every job in the batch reaches `COMPLETED` (mirrors the existing `maybeAdvanceLastSyncTimestamp` "all jobs done" check) — and whether it should run inline (delays the "sync finished" signal) or be dispatched separately. Not implemented yet, flagging the trade-off rather than guessing.
  2. **`PortfolioService.consolidate()` silently undercounts the target and leaves the source stale (High — directly affects anyone who's used Consolidate, e.g. via the FE's `ConsolidateDialog`)**. Root cause: `consolidate()` (`service/PortfolioService.java:85-115`) only does `tx.setPortfolio(target); transactionService.save(tx)` per transaction — never resets `Transaction.processed` and never touches either portfolio's `Holding` rows. Since `CoinInformationService.getCoinInformationResponse` filters to `!transaction.isProcessed()` (`service/CoinInformationService.java:38-40`), and every synced/manually-processed transaction already has `processed=true` from when it lived under its original portfolio, consolidated transactions get silently skipped on the next recompute of the *target* — they never count toward its holdings. Meanwhile the *source* portfolio's `Holding` rows aren't decremented, so it keeps showing balances with no transactions left behind them. Today's only workaround, `/transaction/unprocess?symbol=`, resets that symbol **globally across every portfolio for the user**, not just the two involved — a much bigger hammer than the operation calls for. **Proposed fix**: in `consolidate()`, reset `processed=false` on every moved transaction, and trigger a recompute of the affected symbols on both the source and target portfolios before returning (rather than leaving the caller to remember `/transaction/information/all/{portfolio}` + the global `/unprocess` afterward). **Open question**: whether to do that recompute inline in `consolidate()` (slower endpoint, but leaves the system consistent immediately after the call returns) or just fix the `processed` reset and document that the caller must still trigger recompute for both portfolios — needs a decision, not guessing at it.
